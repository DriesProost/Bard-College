## Data and content design

Create a versioned data package with a manifest plus faculties, skills, lessons, shared studios, review prompts and minimal source metadata. Separate faculty (`writing`/`music`) from existing thematic disciplines. A lesson stores stable ID, content version, stage, objectives, prerequisites, explanation, original good/weak contrasts, short task, optional extension, criterion IDs, review/transfer links, representation assumptions and bounded source references. Distinguish source-supported principles from D-design fields. Runtime validation checks structural integrity; a human checks citation truth and musical/educational accuracy.

Keep every deployed `lesson-*` ID and existing data. Proposed `writing-*`, `music-*` and `combined-*` IDs have not been installed; finalise their manifest once implementation is approved and never reuse an ID later for a different objective. An archived lesson remains readable with its prior evidence. A changed objective gets a review notice, not erased completion. In particular lesson-18 becomes explicitly language tension; old Lute tags do not award Music mastery.

Validate a directed acyclic skill graph, referenced IDs/faculties/sources, per-faculty study order and meaningful review links. The existing loader requires dependencies to appear earlier and has a fixed theme enum; adapt it deliberately rather than concatenate two arrays into the old global chain. Optional shared studios depend on skills in both faculties but never block either independent path. Retain an “attempt diagnostic” route for existing skills without conflating it with verified evidence.

## Preserve SQLite, customised content and progress

Current inspected code uses `attempts(lessonId PRIMARY KEY, body, revision, reflection, completedAt, feedback, feedbackText)` plus projects, snapshots, config, events and usage. Preserve those tables/fields for compatibility. Add schema migration tracking, append-only attempt/evidence records with faculty/skill/criterion/content-version, source draft and reviewer/time, and explicit mappings for historic participation. Use one transaction for each migration and idempotent recovery. Do not rewrite historical XP discipline labels; compute new faculty views through mappings and keep the original events for audit.

Before migration use SQLite's backup API or a closed/checkpoint-aware consistent copy; never copy only the live main file while ignoring its WAL. Verify backup restoration. A failed migration leaves the old version usable or offers restoration, rather than leaving a half-upgraded profile. Credential ciphertext/config is preserved; do not re-encrypt or bind keys to curriculum migration. Existing encrypted-key storage and real connection test remain as previously implemented.

Installed `userData/curriculum.json` can contain user edits and is intentionally not overwritten today. Store/identify the installed base version where available, compare base/user/new-default versions and preview conflicts. Where no trustworthy base version exists, preserve the custom file and require an explicit merge choice; do not guess which edits are expendable. Back up originals; keep both versions until a validated merge is confirmed. Unsupported future formats fail recoverably, without “reset to default”. Custom lesson IDs without faculty mapping keep their work and await a mapping choice, never silently acquire Music credit.

Historical completion remains visible as completion. Show “previously completed; skill evidence not yet reviewed” where appropriate. A later content version may suggest practice without taking away completedAt, XP, original/revised text or earlier feedback. Evidence states are separate from participation. Combined artefacts attach multiple criterion records without copying the project or duplicating rewards. A new readiness graph must not relock or hide a returning learner's completed work.

## AI behaviour and privacy

Keep **GPT-6 Luna exclusively** with the fixed official endpoint and protected credentials. Send the selected original lesson/task/rubric, representation assumptions, necessary learner context, submitted writing/music plan and deliberately selected earlier feedback. Do not send original books, extracted passages, diagrams, publisher access codes or private notes. Bibliographic metadata is not permission to transmit book text. Any future retrieval proposal must specify the exact excerpts/fields/destination/purpose/retention and obtain approval before enabling.

Writing feedback distinguishes comprehensibility, craft choice and taste. Music feedback may assess counted tab/chord/pitch relationships and explanations; it cannot claim to hear timing, melody, voice, groove or performance from text. Report missing evidence instead. Respect intended exceptions and irony; give a reasoned observation, one or two next steps and a question without writing the student's finished song. Preserve source draft/content version with every critique so feedback remains identifiable after revision.

## Verification before release

- Content/graph checks: all 30 deployed IDs remain, final faculty counts are correct, dependency graph has no cycles/missing nodes, each published claim resolves to an actually consulted reference or D-design label, and original tab/diagrams/counts agree.
- Migration/merge fixtures: partial and completed legacy attempts, earlier feedback, snapshots, custom/unknown IDs, absent base versions, interrupted migration/restore, legacy XP and secure credentials. Confirm no duplicate awards or forced re-completion.
- Full journeys: open → goals/faculty → original attempt → optional AI/self-feedback → revision → save → close/restart → reopen; writer-only, music-only and combined. Run offline except explicitly invoked AI.
- Musical/accessibility review: timed tabs and chord diagrams readable at desktop sizes; keyboard navigation/text alternatives; checked capo/tuning/octaves; no staff-only task; simple playable alternatives and human guitar review.
- Tutor tests: exact model, no book contents/access codes in payload, prompt isolation, missing/failed connection preserves edits, stale feedback is identified, no performance claims from text.
- Windows acceptance: installer/update/uninstall, DPAPI, OS restart and reopen, content update/merge, local export and offline operation. Existing cloud validation does not replace a real Windows PC test.
- Learning pilot: test Writing 17/22/29/30 and Music 21/32 time scope, independent explanation and delayed transfer. Review tutor/teacher disagreements. Revise thresholds and content based on evidence rather than gamification.
